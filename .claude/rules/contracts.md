# Contract rules

## Layout
- `src/jury/JurorTreasury.sol` — juror registry and custody of each juror's HBAR. Only the resolver can move money out.
- `src/jury/` (resolver) — case lifecycle, commit-reveal, settlement, the Case Bounty Treasury, and the only caller of the treasury's drawdown functions.
- `src/shares/` — the ATS token interface and `JurorShareMarket`: return-scaled pricing, the 70/30 purchase split, the 2% fee, and the skim distribution.
- `src/anchor/` — Sepolia only. Mirrors finalised results for indexing.
- `test/` for forge tests, `script/` for deploy scripts.

Nothing is vendored. All contract code here is ours.

## Toolchain
- Foundry: `forge build` and `forge test` on both chains. Deploys use a different mechanism per chain; see below. The pnpm scripts in `package.json` wrap these.
- Two RPC endpoints in `foundry.toml`, `hedera` and `sepolia`, both read from env (`${HEDERA_RPC_URL}`, `${SEPOLIA_RPC_URL}`). Never hardcode an RPC URL or a key in a script.
- Foundry only loads `.env` from `packages/contracts/`, not from the repo root. `packages/contracts/.env` is a gitignored symlink to the root `.env`, so there is still one secrets file.
- Inside Hedera's EVM, `msg.value` and balances are in tinybars (8 decimals), while the JSON-RPC relay presents 18-decimal weibars to clients. Keep units explicit everywhere HBAR moves. Verified on testnet with `HederaSmoke`: sending 10¹⁰ weibar arrived as `msg.value == 1`, and the relay reports the contract's balance as 10¹⁰.
- `evm_version = "cancun"` is verified on Hedera testnet: `HederaSmoke.ping` executed MCOPY successfully (tx `0xb87ab4b09a8e487c673ff76b85a7b66c4c80755ee4710c87a9380d4f6b349093`).
- Hedera's relay fills `contractAddress` in the receipt of a plain contract call, not just a deployment. Never infer "a contract was deployed" from `receipt.contractAddress` on Hedera.
- **Hashio rejects `eth_getLogs` inside a JSON-RPC batch**, with `Method eth_getLogs is not permitted as part of batch requests`. ethers v6's `JsonRpcProvider` batches requests by default, so any `Contract.queryFilter`/`getLogs` call against Hashio fails with this error unless the provider is constructed with `{ batchMaxCount: 1 }`. Hit for real reading a case's `caseType` back from its `CaseOpened` event (event-only field, no getter — see below).

## Deploys: two mechanisms, one per chain
- **Sepolia deploys with `forge script script/DeploySepolia.s.sol`.** Deploys `NyayaAnchor` and fresh `UserRegistry`/`PermissionedResolver` ENSv2 instances, wires nyaya.eth to the fresh instances (`setSubregistry`/`setResolver`), and re-registers the three juror subnames with Enhanced Access Control — one broadcast, nothing left as a manual follow-up. nyaya.eth itself and the three juror identities are read from the existing `deployments/sepolia.json` and reused, never redeployed: a name registration isn't a redeployable contract, and re-registering it would need a fresh 60-second commit-reveal wait for no reason. Needs `fs_permissions = [{ access = "read-write", path = "deployments/" }]` under `[profile.default]` in `foundry.toml` — inside `[lint]` or any other table silently does nothing and the read reverts.
- **Hedera deploys with `script/deploy-hedera.sh`, `forge create` and `cast send`, never `forge script`.** `forge script` cannot target Hedera through Hashio, Hedera's public JSON-RPC relay. To simulate, `forge script` forks the chain pinned to a block hash and sends EIP-1898 block parameters such as `eth_getTransactionCount(addr, {"blockHash": …})`. Hashio rejects that object form for every method, and rejects a bare block hash for `eth_getCode`; it accepts only hex block numbers and tags like `"latest"`. `--fork-block-number` does not help, because Foundry converts the number back to a hash. This was tested directly against Hashio with Foundry 1.8.1, not assumed. `forge create` does not fork, and its requests use `"latest"`, which Hashio accepts. Deploys `JurorTreasury`, `NyayaResolver`, wires `treasury.setResolver(resolver)`, then `JurorShareMarket` — genesis withdrawal cap/window match the values already live on the previously deployed treasury, read on-chain before being written into the script, not guessed.
- Both mechanisms write addresses to a committed JSON per network so the other packages read them from one place. Never paste an address into more than one file.
- Every real deploy rewrites that network's JSON entry for every contract it deployed, unconditionally, even if the deploy was unexpected or a repeat. `forge script --broadcast` is pre-approved in `.claude/settings.json`, so this is the guard against a stray deploy leaving another package pointing at a stale address. `deployments/hedera.json`'s `contracts` map and `deployments/sepolia.json`'s `contracts` map are each fully replaced, not merged key-by-key; unrelated top-level keys the deploy doesn't touch (ATS factory/resolver ids, per-juror share tokens and distributors on Hedera) are carried forward as-is.
- **Sepolia dry-run guard:** a `forge script` run without `--broadcast` must never write the JSON. Its addresses were only simulated and exist on no chain. Use `vm.isContext(VmSafe.ForgeContext.ScriptBroadcast)` to tell a broadcast from a dry run. **Verified by actually running the script both ways, not assumed** (flagged as untested since step 1, closed in step 12): `script/verify-sepolia-deploy-guard.sh` forks live Sepolia with a local anvil (real ENSv2 contract code, zero real cost), runs the deploy script once without `--broadcast` and asserts the address file is byte-for-byte unchanged, then once with `--broadcast` and asserts the file changed and every written address is well-formed, restoring the real file afterward unconditionally via a trap. `test/DeploySepolia.t.sol` separately cross-checks the script's role-bitmap literals against an independent bit-shift recomputation and against the exact decimal values step 10 confirmed on-chain — a free local test, not a substitute for the anvil run, which is the only thing that exercises `isContext` in its two real states (`forge test`'s own context is neither `ScriptDryRun` nor `ScriptBroadcast`, so the guard can't be exercised meaningfully from inside a plain forge test).
- **Hedera write rule:** `forge create` has no separate simulate-then-broadcast phase, so the Hedera script needs no dry-run guard. Instead, it writes an address only after `forge create --broadcast` has returned a real deployed address and transaction hash, parsed from `forge create --json` output (`deployedTo`, `transactionHash`), never from a guess or a precomputed address.
- **Preflight a balance check before spending anything**, same discipline as every individual script this project has run: `deploy-hedera.sh` checks the operator's Hedera balance against a named floor before deploying anything and aborts with a clear message (and the faucet to use) if short, rather than deploying partway and failing on the second or third contract. **Do that division in Python (or similar), never in bash's native `$(( ))`**: a weibar balance is an 18-decimal number and routinely exceeds bash's 64-bit signed integer range, which overflows silently rather than erroring — it once reported an operator holding 55 HBAR as holding 0.12 HBAR, and the script aborted a real deploy on a false low-balance reading.
- **`forge create --constructor-args` consumes every token after it as an argument.** Any flag placed after `--constructor-args ... <values>` (an `--rpc-url`, a `--broadcast`) is silently swallowed as an extra constructor argument instead of being parsed as a flag, and `forge create` then falls back to its default RPC (`http://localhost:8545`) with a connection-refused error that looks like a network problem, not an argument-order problem. Put `--constructor-args` and its values last, after every other flag.
- **A one-time setter with no override (`JurorTreasury.setResolver`, `NyayaResolver.setDistributionAddress`) or an `immutable` set at construction (`JurorShareMarket.resolver`/`treasury`, `JurorShareDistributor.resolver`) cannot be undone by a script, only by redeploying the contract that holds it.** Before writing to one of these from a script, confirm on-chain what it already holds, never infer that from a deployments-file entry: a `distributors`/`shareTokens`-style bookkeeping entry can describe a superseded contract, and treating its presence alone as "already correctly wired" pointed a live resolver's permanent `distributionAddress` at a distributor bound to a different, incompatible resolver. The fix that prevents recurrence: read the candidate's own on-chain state (here, the distributor's own `resolver()`) and compare it to the currently-live contract it would need to reference before ever reusing it; deploy fresh and say why, rather than reuse, on any mismatch.
- **ATS's control list lives on the token and survives a market redeploy; `JurorShareMarket.registerShareToken` did not originally account for that.** It called `token.addToControlList(juror)` / `(hotWallet)` unconditionally, which reverts ATS's real `ListedAccount(address)` for an address a *previous* market instance already registered — a real contract bug a market redeploy exposes, not a wiring gap. Fixed by checking `token.isInControlList(...)` first and skipping the call if already true; `test/mocks/MockAtsToken.sol`'s `addToControlList` now reverts `ListedAccount` on a duplicate too, matching real ATS instead of silently succeeding. Also confirmed nothing else in `JurorShareMarket.sol` shares this shape (an external call assuming a one-time, never-yet-done state): `fund`, `contributeToCaseBountyTreasury`, `mint`, `burn`, and the ETH transfer in `sell` are all meant to run every time, not once, so they were never at risk.
- **Registering a juror on a fresh treasury is a real prerequisite `registerShareToken` depends on** (`treasury.hotWalletOf(juror)` must resolve), and it is operator-only — it needs the juror's already-public address and hot wallet, never the juror's own signature. A Hedera deploy that omits juror registration (this project's does, deliberately, since juror identities aren't deploy-time concerns) means any post-redeploy ATS wiring must register the relevant jurors again before it can proceed.

## What the resolver must implement
- **Two ways to open a case.** `openCase()` is permissionless, with the bounty attached as `msg.value`. A separate operator-gated function opens a case funded from the Case Bounty Treasury balance, which the resolver holds. Record each case's bounty source in the `CaseOpened` event.
- **Three jurors, equal genesis treasury.** Every juror rules on every case. No panel selection, no majority vote, no tier-based stake ceilings.
- **Commit-reveal.** A commitment is `keccak256(abi.encode(caseId, juror, ruling, confidence, salt))`. The case id and juror address are bound in so a juror cannot copy another's commitment and then replay its reveal. Commits close at the commit deadline, and reveals open after it. A reveal carries ruling, confidence, salt, and the IPFS CID of the juror's evidence trail, and nothing else. There is no spend field. Only the CID goes on-chain. A juror that commits but does not reveal is slashed as incorrect.
- **`Ruling` enum, fixed:** `enum Ruling { None, No, Yes }` in `NyayaResolver`. `abi.encode` writes it as its index (None = 0, No = 1, Yes = 2), so never reorder it. `None` can never be revealed.
- **Commit signature:** `function commit(uint256 caseId, bytes32 commitment, uint256 stake) external;`. The caller is the juror, and the stake is locked through `JurorTreasury.lockStake`. The contract's `commitmentFor(caseId, juror, ruling, confidenceBps, salt)` is a pure helper that returns the exact hash, so an agent can check its own encoding with an `eth_call`.
- **Reveal window:** from the commit deadline (inclusive) to the resolution time (exclusive). Revealing early would leak a ruling to jurors who haven't committed yet, and closing at the resolution time means every reveal is final before an outcome can be reported.
- **Reveal signature, fixed; the agent calls it exactly as written:**
  ```solidity
  function reveal(uint256 caseId, Ruling ruling, uint16 confidenceBps, bytes32 salt, string calldata evidenceCid) external;
  ```
  - The juror is not a parameter. The contract recomputes the commitment with `msg.sender` as `juror`, which is what makes a copied commitment fail.
  - The `confidence` in the commitment is this `uint16 confidenceBps`. `abi.encode` pads every field by type, so the agent must hash the same five fields in the same order with the same types.
  - `evidenceCid` is a `string` because Pinata's CIDs don't fit cleanly into `bytes32` without an encoding step on both the write side and the read side. A `string` avoids that entirely. Reveal is a low-frequency, write-once call, so the gas saved by `bytes32` isn't worth two codebases having to agree on a byte format.
- **Confidence-scaled stake, locked at commit.** Stake is locked in the juror's `JurorTreasury` balance by the resolver when the juror commits. The contract records stated confidence but does not verify it. Scaling stake to confidence is agent policy.
- **Outcome submission.** Only the operator submits a case outcome, only inside the window defined under "Grace boundary" below, and always with the IPFS CID of the resolution checker's raw evidence. Only the CID goes on-chain, never the evidence itself. This is the only off-chain input to settlement. Never add another.
- **Grace boundary.** `graceEnd = resolutionTime + 24 hours`. `submitOutcome` requires `resolutionTime <= block.timestamp < graceEnd`. From `graceEnd` onward it reverts unconditionally, including for the operator. Cancellation requires `block.timestamp >= graceEnd` and no outcome submitted. Using one boundary for both means there is no overlap, so a late submission and a cancellation can never race, and no gap in which neither path is open.
- **Cancellation.** Anyone can cancel, not just the operator. Cancellation refunds every committed juror's full stake, whether or not it revealed, and returns the bounty to its recorded source. Keep this a separate code path from the non-reveal forfeit. A non-reveal is a juror's choice and forfeits the stake; a missing outcome is a platform failure and refunds it.
- **Cancelled-case spend is still a loss.** For each juror with case-tagged withdrawals on a cancelled case, add that `x402Spend` to cumulative capital and subtract it from cumulative net. The refunded stake adds nothing to either total. Emit it as a cancelled-case loss, distinct from an incorrect-ruling loss, even though the accounting is the same.
- **Settlement math, deterministic given the outcome:**
  - `P = bounty + Σ stake` of incorrect and unrevealed jurors `+ rolloverPool`; `S = Σ stake` of correct jurors.
  - Settlement iterates the case's participants: every juror that committed or withdrew evidence money for it. Each gets a `JurorSettled` event with a `Result`: `Correct`, `Incorrect`, `Unrevealed`, or `NoCommitment` (spent on evidence but never committed; net `−x402Spend` on capital `x402Spend`). Losses share accounting but keep their cause.
  - `NoCommitment` is not by definition a bug: an agent below its confidence threshold (see `.claude/rules/agent.md`) deliberately declines to commit after spending, and that is a legitimate policy decision. It can also still mean a genuine agent bug (a crash, a missed deadline, a failed transaction) — the on-chain accounting can't distinguish the two causes, only the agent's own reasoning trail can. Alongside the normal accounting, settlement emits `SpentWithoutCommitting(caseId, juror, x402Spend)` as a "juror declined to rule" signal to watch, not an automatic alert. Keep this event additive: it must never change the math.
  - Correct juror: stake returned plus `reward = P · stake / S`. Proportional to stake, never an equal split.
  - Incorrect or unrevealed juror: whole stake slashed into `P`.
  - `x402Spend` is the sum of the juror's withdrawals tagged with this case id. Settlement reads it only from that history, never from anything the juror submits.
  - `net = reward − x402Spend` if correct, `−stake − x402Spend` if not. Never drop the x402 term.
  - `return = net / (stake + x402Spend)`. This is the per-case figure. Return-scaled pricing reads the juror's cumulative return since genesis, `Σ net / Σ (stake + x402Spend)` over all its settled cases, pre-skim. Store it as two per-juror running totals: signed cumulative net and cumulative capital. Never a mean of per-case percentages, and no sliding window.
  - Skim: `skim = floor(net × SKIM_BPS / 10000)`, with `SKIM_BPS = 2000`, on positive net only. No skim on a loss, including a correct juror that spent more than it won.
    - The juror's treasury is credited `reward − skim`. It is never an independently computed 80%, so skim plus what's kept always adds back to the net exactly.
    - The skim is held per juror in `pendingDistribution`. `releaseDistribution(juror)` is permissionless and sends it only to that juror's `distributionAddress`, which the operator sets once. That address is what feeds ATS mass payout to holders, and it is wired up when the shares are issued.
    - `Skimmed(caseId, juror, skim, retainedNet)` is emitted separately from `JurorSettled`.
    - **The track record is pre-skim.** `cumulativeNet`, `returnBps` and `JurorSettled.net` never subtract the skim. There is a test for exactly this.
  - No correct jurors: return the bounty to its source and add the slashed stakes to `rolloverPool` and set `rolloverUpdatedAt`. The rollover joins the pool of the next case that settles with a correct juror and has `commitDeadline > rolloverUpdatedAt`. A case whose commits closed before the rollover existed never receives it. `CaseSettled` reports `rolledIn` and `rolledOut` separately. External openers are credited to `refundOf` and pull the money with `withdrawRefund()`, never pushed, so a reverting opener can't block settlement. Treasury-sourced bounties go back to `caseBountyTreasury`.
  - `returnBps(juror)` = `cumulativeNet × 10000 / cumulativeCapital`, rounded toward zero. This is what the price reads.
  - Rounding: every payout is rounded down to the tinybar. Whatever is left of the pool after paying correct jurors goes to the Case Bounty Treasury, never to an individual juror. The skim is `floor(net × 20 / 100)` and the treasury credit is `net − skim`, so the skim leaves no remainder.
- **Treasury drawdown paths.** `JurorTreasury` has exactly three ways money leaves a juror's balance, all resolver-only:
  - `lockStake`
  - `slashStake`, which sends the stake to the resolver and never back to the juror
  - `withdrawForX402`

  `unlockStake` returns a locked stake to the juror. Funding (`fund`) is open to anyone. Never add a juror-callable withdrawal. The withdrawal cap and window are constructor values set at deploy.
- **Evidence withdrawals go through the resolver.** A juror calls `withdrawForEvidence(caseId, amount)`, allowed only before the case's commit deadline, and the resolver calls `JurorTreasury.withdrawForX402`.
- **x402 withdrawal path.** A capped, rate-limited withdrawal from a juror's treasury to its hot wallet, tagged with a case id at withdrawal time. The withdrawn amount counts as that case's `x402Spend`, and this is the only source settlement uses for spend. This is a documented trust leak: the contract cannot verify where the money went after it leaves.

## ATS scripts
- They live in `packages/contracts/script/ats/`, TypeScript run with `tsx`, because they write the same `deployments/hedera.json` the Hedera deploy path maintains and they exist to serve the Solidity in this package. Keeping them here means one address file and one place where ATS wiring lives.
- Call ATS's contracts with ethers. The SDK has no headless signer, so it cannot be driven from a Node script holding a private key; see CLAUDE.md for the full reason. `atsConfig.ts` loads ATS's own published `IFactory` ABI from the contracts package and falls back to transcribed fragments only if that path moves.
- Roles are granted inside `deployEquity` through `SecurityData.rbacs`, not in separate transactions: the market gets `ROLE_ISSUER`, `ROLE_CONTROLLER` and `ROLE_CONTROL_LIST` as the token is created.
- Two creation flags decide whether the compliance test means anything: `isWhiteList: false` (blacklist mode, so listed addresses are the blocked ones) and `internalKycActivated: false` (so an ordinary buyer needs no identity flow). Whitelist mode would invert the test and it would silently prove nothing.
- ATS's testnet factory and resolver ids come from `apps/ats/web/.env.example` on the ATS repo. The SDK README lists an older pair, so the scripts verify the address has code before using it and let `ATS_FACTORY_ID` / `ATS_RESOLVER_ID` override.
- **In scripts, convert before comparing: provider balances are weibar (18 decimals), everything a contract reports is tinybars (8).** Comparing a balance delta against a contract figure makes a correct payout look wrong by a factor of 10¹⁰, which reads as a contract bug. This produced a false "real ATS differs from the mock" result once.
- **Take ABIs from artifacts, not hand-written fragments**: `artifactAbi("NyayaResolver")` for our contracts, `atsAssetAbi()` for the ATS token. A hand-written list silently omits functions, which surfaces mid-run as `x is not a function` after earlier transactions have already spent gas.
- **Run `assertFunctionsExist` at the top of any script**, listing every function it intends to call per contract. Same class of bug as the ATS struct mismatches and the same fix: fail offline, by name, before anything is sent.
- Build every ATS struct from the artifact's components, and run `assertMatchesAbi` before sending. It fails offline, by field name, instead of as an encoder error mid-run. A missing `putRight` cost one run's gas.
- **`assertMatchesAbi` catches structural mismatches only, and by design cannot catch value-validity rejections.** A perfectly shaped struct with a bad ISIN check digit or a forbidden regulation pair encodes fine and reverts on-chain, after gas. `assertValidEquityValues` exists for that second class and mirrors every by-value check in ATS's `Factory.sol` v8.0.0: `_validateISIN` (`WrongISIN` for a length other than 12, `WrongISINChecksum` = `0x342c92db` for a bad ISO 6166 check digit), `EmptyResolver`, `NoInitialAdmins` (rbacs must include DEFAULT_ADMIN with a non-zero member) and `_checkRegulationTypeAndSubType`. When ATS adds a check, add it there too; anything left out is only discoverable by spending gas.
- Values the ABI does not determine, taken from ATS's source: **`maxSupply` must be non-zero at deployment** — ATS reverts with `NewMaxSupplyCannotBeZero()`, even though its mint path treats a zero cap as "uncapped", so the source reads as if 0 were fine; `regulationType` must be REG_S (1) with subtype NONE (0), or REG_D (2) with a 506 subtype, because `_isValidTypeAndSubType` rejects NONE/NONE; `dividendRight: 2` is `DividendType.COMMON`. REG_S records a resale hold period, but that field appears nowhere in ATS's transfer enforcement, so it does not restrict trading.
- **`resolverProxyConfiguration.version` must be resolved, never hardcoded to 0.** ATS's web app leaves the version blank and the SDK fills it in; calling the contracts directly means asking the resolver with `getLatestVersionByConfiguration`. Version 0 does not exist (testnet's equity configuration is at version 1) and the lookup then reverts with no data.
- **Hedera footgun 1: a contract has two EVM addresses, and Solidity equality between them fails.** Every entity has a long-zero address derived from its id (`0x…008c9142` for 0.0.9212226) and an alias (`0xba2d5f…`). Both route calls to the same contract, so `eth_getCode` and read calls succeed on either, which makes the wrong one look fine. But as 20-byte values they are unequal, so any stored-value comparison or address-keyed lookup misses. ATS stores its resolver's alias, and passing the long-zero form to `deployEquity` reverts with **no data at all**. Resolve the alias from the mirror node (`/api/v1/contracts/{id}` returns `evm_address`); never derive an address that will be compared, only ones that are called.
- **Hedera footgun 2: never let ethers estimate gas for a call that deploys a contract.** `deployEquity` deploys a proxy, and the relay's simulation path for `eth_call` and `eth_estimateGas` reverts such calls with empty data and `CONTRACT_REVERT_EXECUTED`, whatever the arguments. Pass an explicit `gasLimit` (Hedera caps a transaction at 15M gas) so the transaction actually executes; a real receipt and HashScan carry a far more specific error than the simulation does. The same relay simulation is fine for ordinary calls, which is why the blocked-buy `eth_call` in the proof script still works.
- **Hedera footgun 3: the sender must hold `gasLimit × gasPrice + value` up front, whatever the call actually burns.** An oversized gas limit therefore fails a perfectly well-funded account, and it surfaces as a generic insufficient-funds error that reads like underfunding. At ~1140 gwei, a 15M limit reserves 17.1 HBAR while the call may burn 100k. Size each limit to its call and keep them in separate named constants, never one shared value: deploying a proxy needs millions, a call that reverts at a compliance check needs under 200k. Check `balance >= gasLimit × gasPrice + value` before sending and report which component is short.
- **Hedera footgun 4: the relay refuses to broadcast a transaction it predicts will revert.** A deliberately failing call (proving a compliance block, say) then produces no hash at all, only a local error. Sign it and send it with `provider.broadcastTransaction`, with an explicit `gasLimit`, so it lands with status 0 and a judge can open it. The relay's receipt carries no revert data; read `error_message` from the mirror node's `/api/v1/contracts/results/{hash}` and decode the selector.
- Record every testnet transaction that proves a step in `docs/TESTNET-EVIDENCE.md`. That file, not a passing mock test, is what discharges the "a mock alone is not evidence" rule.
- ATS's `deployEquity` selector changed between package versions (`0xfb3c59d8` in v6 and v7, `0x837b37b6` in v8) because the struct field order changed. The deployed factory is a resolver-proxy: an unknown selector reverts with its own error data, so an empty-data revert means the selector resolved and execution failed later. Use that to tell the two apart instead of guessing.
- Scripts must be re-runnable without re-spending: reuse funded accounts when `JUROR_PK`/`HOT_PK` are given, top up only the shortfall, and skip one-time steps such as `registerJuror` when already done.
- Accounts the scripts generate are throwaway testnet keys. Print them for inspection; never write them to a file in the repo or to `.env`, and never reuse them.
- The third-party buyer must be a different account from the operator. A buy from the account that runs everything only shows an unblocked address can buy, which proves nothing about the control list distinguishing accounts.

## ENS scripts
- They live in `packages/contracts/script/ens/`, TypeScript run with `tsx`, writing `deployments/sepolia.json` the same way the ATS scripts write `deployments/hedera.json`: our own deployed instances (the `UserRegistry` and `PermissionedResolver` proxies, `nyaya.eth`'s tokenId, each juror subname), never the ENSv2 protocol's own addresses, which live in `ensConfig.ts`'s `ENS_ADDRESSES` as verified defaults with an env override, the same pattern as `ATS_FACTORY_ID`/`ATS_RESOLVER_ID`.
- No SDK, same reason class as ATS: `contracts-v2` isn't published to npm at all (`@ensdomains/verifiable-factory` is, and its ABI is used the same way). ABIs are the literal compiled `abi` field from `contracts-v2`'s own `contracts/deployments/sepolia/<Name>.json` at the pinned commit, saved into `script/ens/abi/`, not hand-transcribed and not the SDK's.
- **Verify every protocol address two ways before trusting it**: matched byte-for-byte against the pinned-commit deployment manifest, and confirmed to have code on Sepolia via `cast code`. A prompt handing you "verified" addresses is not itself verification.
- `IRegistry.getSubregistry(label)` / `getResolver(label)` take the **label string** ("nyaya"), not the tokenId/anyId that `IStandardRegistry.setSubregistry(anyId, ...)` / `setResolver(anyId, ...)` take. Passing a tokenId to the getters doesn't revert — ethers just ABI-encodes whatever you pass as the declared `string` type — so it silently reads back the wrong (empty) entry and looks exactly like a failed write. Caught by re-reading with the correct label after the writes had already succeeded.
- `LibLabel.id(label) = uint256(keccak256(bytes(label)))` is a **plain per-level labelhash**, scoped to whichever registry instance holds that label — it is not the recursive DNS `namehash` of the full name. Registry-level lookups (`getState`, `getTokenId`, `LibLabel.id`) use the plain labelhash of one label; resolver-level EAC and record lookups (`authorizeTextRoles`, `setText`, `text`) use the full DNS namehash of the whole name (`NameCoder.namehash`, matching ethers' `namehash()`/`dnsEncode()` exactly — confirmed by reading `NameCoder.sol`'s labelhash step, which is the same `keccak256` ENSIP-1 uses). Using one where the other is expected doesn't revert; it just resolves a different, usually-empty, entry.
- **A commit-reveal wait must be timed from the commitment's on-chain timestamp, not from a wall-clock value captured before the commit transaction is sent.** Broadcast and confirmation can themselves take longer than a small safety margin covers, so a wait computed from an earlier local timestamp can undercount and let `register()` fire while `MIN_COMMITMENT_AGE` hasn't actually elapsed on-chain yet, reverting `CommitmentTooNew`. Re-read `commitmentAt(commitment)` after committing and wait from that.
- **Register `nyaya.eth` with subregistry and resolver left at zero, not the real addresses.** `ETHRegistrar.register()`'s commitment binds both, which would force deploying them before the commit; instead, `_register()` (read directly, not assumed) grants the owner `ROLE_SET_SUBREGISTRY`/`ROLE_SET_RESOLVER` (with admin variants) on the name's own resource regardless, and accepts a zero registry/resolver without reverting. Deploy them after, then wire them on with `setSubregistry`/`setResolver` using that granted role. This is also why the deploy scripts are split into small numbered steps: each one can fail and retry independently instead of one script needing everything to succeed in order.
- **A failed `send()` must recover the real revert data, not just report a transaction hash.** A plain `Error` thrown from a failed receipt gives `revertName()` nothing to decode, which reads as "reverted with no data" whether or not the chain actually returned any — this hid a real `CommitmentTooNew` once. Replay the same call as `eth_call` at the receipt's block to recover it; a public Sepolia RPC endpoint supports this directly, unlike Hedera's Hashio, which is why step 7's Hedera evidence needed the mirror node instead.
- **Enhanced Access Control roles held at `ROOT_RESOURCE` cascade to every other resource** (`_effectiveRoles` in `EnhancedAccessControl.sol` ORs `ROOT_RESOURCE` roles into any resource's check unconditionally). Grant the operator broadly at root once per contract instance rather than per-subname; grant a juror's own key narrowly, per-subname and per-text-key-part (`authorizeTextRoles`), never at `resource(node, 0)` ("any field of this name") and never on `score`/`returnRate`, or it could write its own score.
- Juror keys for the three subnames are fresh throwaway keys generated by the scripts, the same rule as the ATS jurors: printed for inspection, never written to `.env` or a repo file, never reused. Only each juror's **address** is persisted to `deployments/sepolia.json`; a later step that needs to sign as the juror takes the private key back in via an env var supplied fresh at invocation, and checks it derives the recorded address before using it.
- Prove the EAC split with a positive control, not just the rejection: a juror writing `profile` must succeed before a juror's `score` write failing means anything, otherwise the failure would be equally true of a juror that can write nothing at all. Assert the specific `EACUnauthorizedAccountRoles` error, not merely that the call reverted, the same discipline as ATS's `AccountIsBlocked`.

## Anchor and relay scripts
- `src/anchor/NyayaAnchor.sol` is Sepolia-only, operator-gated, and append-only: it holds historical settlement events for indexing, never a juror's current state. Keep it separate in purpose from the ENSv2 resolver in `script/ens/`, even though both are on Sepolia — the resolver holds one overwritten snapshot per juror, the anchor holds every event. Never route an anchor write through the resolver's text records, or vice versa.
- **Every numeric field the anchor emits is a tinybar (Hedera's 8-decimal unit), not an 18-decimal Sepolia-native value**, because it mirrors what the Hedera resolver and distributor actually store. The one exception is `Distribution.amountPerUnit` on a `Declared` row, which carries the distributor's own fixed-point scaling and is not a plain tinybar figure at all. State this in the contract's own comments at the point a future reader would need it, not only in this file — this is exactly the unit-confusion class that produced a false ATS-divergence report one layer down (see the ATS scripts section above), one layer up.
- The anchor's own enums (`Result`, `Ruling`) must mirror `NyayaResolver`'s exactly, index for index — they can't share a type across chains, so they're redeclared, and redeclaring them wrong would silently misdecode every downstream indexer.
- Relay scripts live in `packages/contracts/script/anchor/`, read Hedera, write Sepolia, and are manually invoked — proving the anchor works, not a watcher. **Read a known transaction's receipt (`provider.getTransactionReceipt(hash)`), never a ranged `eth_getLogs`/mirror-node topic query**: Hashio rejects any topic-filtered log range over 7 days, and this project's testnet history already exceeds that. A single transaction has no such limit, whichever endpoint answers it.
- **An artifact ABI reflects the current source, not necessarily what's deployed.** The resolver at the address in `deployments/hedera.json` predates step 9's `bountySource` field on the `Case` struct, so decoding its `cases()` return with the current 8-field ABI corrupts every field after `resolutionTime` — an 8-field decoder reading 7 actual words shifts everything past the mismatch. This is a real failure this step hit, not a hypothetical: a function whose on-chain shape has since changed needs a hand-written legacy ABI fragment matching what's actually deployed, not the compiled artifact. The rule elsewhere in this file about hand-transcribed ABIs being unsafe cuts the other way here — it's the up-to-date artifact that's wrong for an old deployment.
- **A relay must confirm the data it reads is still current, not assume it.** `cumulativeNet`/`cumulativeCapital` are running totals; reading them live is only a valid checkpoint for the case being relayed if no later case has also settled or been cancelled for that same juror. Check that on-chain (via the case's own `settled`/`cancelled` flags, not by assuming) before relaying, and refuse to relay if it doesn't hold, rather than silently mislabeling a later case's effect as this one's.
- A relayed case is reused from real prior testnet activity, never opened fresh for the relay's own sake — the same "make retries cheap" instinct as reusing funded accounts elsewhere in this file.

## Share rules
- A share purchase splits its trade value 70% to the juror's treasury in the resolver and 30% to the redemption reserve. Redemptions pay out only from the reserve.
- A 2% fee on trade value is charged on top of every trade: added to what a buyer pays, subtracted from what a seller receives. It accrues to the Case Bounty Treasury in the resolver. It is never carved out of the 70/30 split, so keep the fee and the split as separate code paths acting on separate amounts.
- **The skim is paid by `JurorShareDistributor`, one per juror**, set as that juror's `distributionAddress` in the resolver. `receive()` accepts HBAR only from the resolver. `declare()` (operator, needs `ROLE_CORPORATE_ACTION` on the token) turns everything received into one ATS dividend with `recordDate = now`, so ATS snapshots holders and computes each entitlement; holders then `claim()` and this contract pays. ATS declares and calculates, we pay: that is what makes "declared through ATS, paid by our distributor" literal. A claim is capped at the pot remaining, so rounding or a supply that grew after the snapshot can never overpay, and `reclaimUnclaimed` returns a stale remainder to the pool after 30 days instead of stranding it.
- **Pricing is return-scaled, with no supply term:** `price = max(BASE_PRICE × (10000 + returnBps) / 10000, MIN_PRICE)`, reading the resolver's cumulative pre-skim `returnBps`. Never add a supply term, and never call it a bonding curve. A supply term would make price track trading volume as well as judgment quality.
- Redemptions are paid only from that juror's own reserve, at the current price. A sale the reserve cannot cover reverts in full; never part-pay it and never touch another juror's reserve.
- **ATS does the compliance blocking. We never repeat it.** Registering a juror's token adds that juror's key and hot wallet to the token's control list (needs `ROLE_CONTROL_LIST`), and ATS's own `mint` compliance check then rejects purchases from them with `AccountIsBlocked`. Do not add a matching check in our market: ours would fire first, and ATS's compliance registry would become decorative rather than load-bearing, which is the opposite of what the Hedera track rewards and of what `SPONSOR-REQUIREMENTS.md` claims.
- Tests for blocking must assert the specific ATS error (`AccountIsBlocked` with the blocked address), never just that the call reverted. A bare "it reverts" assertion passes for unrelated reasons and proves nothing about ATS.
- The market needs three roles on each juror's token: `ROLE_ISSUER` to mint on a buy, `ROLE_CONTROLLER` to burn on a sell, and `ROLE_CONTROL_LIST` to register the blocks. ATS checks roles before compliance, so a missing role surfaces as `AccountHasNoRoles`.
- **`MockAtsToken` is for iteration speed only; it is not evidence.** It mirrors ATS v8.0.0's modifiers, error selectors and their evaluation order, and it must keep mirroring them: a mock that blocks correctly but reverts differently hides exactly the bug class it exists to catch. The evidence is a real ATS token on Hedera testnet with recorded transaction hashes for a successful third-party buy and a rejected buy from each juror-owned address. Forking is not an option: Hashio rejects the EIP-1898 block-hash parameters forge's forking depends on, tested directly, the same limitation that split the deploy path in two.
- A juror's own key and hot wallet must be blocked from holding that juror's shares. This is the anti-wash-trading control and it is a judged feature, not an optional guard.

## Events
Every state change the subgraph or UI needs must emit an event: commit, reveal (with evidence-trail CID), outcome submission (with evidence CID), per-juror settlement (stake, spend, reward, net, return, skim), spent-without-committing alert, pool remainder to the Case Bounty Treasury, cancellation (with each refund and each juror's recorded cancelled-case spend), withdrawal (with case id), share trade, distribution. The subgraph rebuilds state from event deltas and must never need an RPC call per record.

## Testing
- Forge tests are for logic. A test that passes against a mock but has never run against testnet is not evidence. After any resolver or share change, run the real end-to-end script against Hedera testnet and report the transaction hash.
- Keep a test that reproduces the worked example in `docs/ARCHITECTURE.md` (A, B and C, a 20 HBAR bounty). It asserts the rounded-down tinybar payouts exactly: A 4,166,666,666, B 833,333,333, and 1 tinybar to the Case Bounty Treasury. It checks the return identity by cross-multiplication, `(P·s_A − x_A·S)·(s_B + x_B) == (P·s_B − x_B·S)·(s_A + x_A)`, never by comparing rounded percentages.
